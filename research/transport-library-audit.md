## Ray hit provider from three mesh bvh

The `three-mesh-bvh/webgpu` entry exports `BVHComputeData`, TSL structs and function nodes. Construct it from scene objects, geometry or a geometry BVH and call `update()` before dispatch. Its documented `storage` and `fns` provide GPU buffers and `fns.raycastFirstHit`. `rayStruct` accepts **origin, direction and maxDist**, so probe rays can originate anywhere rather than only at a camera. `maxDist=0` means unbounded. The hit struct returns distance, normal, barycentrics, triangle indices, side and a packed object/transform index. [Public entry](https://github.com/gkjohnson/three-mesh-bvh/blob/26fc97c5f007b8bd905ec31df9deac5d9d668782/src/webgpu/index.js), [compute data](https://github.com/gkjohnson/three-mesh-bvh/blob/26fc97c5f007b8bd905ec31df9deac5d9d668782/src/webgpu/BVHComputeData.js), [ray and hit structs](https://github.com/gkjohnson/three-mesh-bvh/blob/26fc97c5f007b8bd905ec31df9deac5d9d668782/src/webgpu/tsl/structs.js).

The standard first-hit implementation transforms the ray into object space, accounts for direction-length scaling, finds the closest triangle and transforms the normal back with the inverse transpose. It returns a side sign and a ray-facing normal, so a DDGI adapter must explicitly recover/preserve geometric face orientation for backface classification. It is not automatically equivalent to the native signed-hit convention. The lower-level public `getShapecastFn` supports custom intersection callbacks, including application-specific filtering. [First-hit implementation](https://github.com/gkjohnson/three-mesh-bvh/blob/26fc97c5f007b8bd905ec31df9deac5d9d668782/src/webgpu/shapecastFns/getRaycastFirstHitFn.js), [triangle intersection](https://github.com/gkjohnson/three-mesh-bvh/blob/26fc97c5f007b8bd905ec31df9deac5d9d668782/src/webgpu/tsl/fns.js).

This is an intersection library, not a complete transport renderer. The provider must map packed object/triangle identifiers to our scene/material IDs and define opacity, sidedness and shadow behavior. The default first-hit function does not evaluate a glTF material, light, alpha texture or BSDF. Begin with opaque triangles and our already calibrated diffuse light contract; add material-aware traversal deliberately.

## Scene updates and instancing

`BVHComputeData.updateTransforms()` refits the clustered scene BVH and rewrites transforms/visibility without rebuilding all GPU storage. Structural changes require `update()`; `updateAsync()` can await an overridden BVH builder. The inspected implementation still lists finer automatic geometry/attribute change detection as TODO work. Do not assume a modified vertex buffer or morph state has been detected and uploaded merely because a transform refit ran. Its WebGPU API is explicitly marked unstable. [Update contract and implementation](https://github.com/gkjohnson/three-mesh-bvh/blob/26fc97c5f007b8bd905ec31df9deac5d9d668782/src/webgpu/BVHComputeData.js).

Source paths cover `InstancedMesh`, `BatchedMesh` and `SkinnedMeshBVH`. The clustered BVH includes instance transforms and distinct BatchedMesh geometry ranges; it does not justify an unlimited-instance or arbitrary-deformation claim. Changing instance counts, groups, geometry or topology needs a rebuild test. Skinned/morphed content needs explicit BVH refit plus refreshed packed attributes, rather than relying on the transform-only path. Stack depth, buffer size, material groups and per-device limits remain compatibility gates. [Clustered scene implementation](https://github.com/gkjohnson/three-mesh-bvh/blob/26fc97c5f007b8bd905ec31df9deac5d9d668782/src/webgpu/ClusteredBVH.js).

The pinned TypeScript declaration exposes `storage`/`fns` largely as `unknown` and omits some documented runtime methods, including `updateTransforms`. A narrow adapter declaration may be needed; this is separate from runtime support. [Pinned declarations](https://github.com/gkjohnson/three-mesh-bvh/blob/26fc97c5f007b8bd905ec31df9deac5d9d668782/src/webgpu/index.d.ts).

## What the path tracer offers

`three-gpu-pathtracer/webgpu` exports `WebGPUPathTracer` and rendering utilities. Public operations cover `setScene`, worker-assisted `setSceneAsync`, `renderSample`, material/light/environment updates, transform updates, sample-count queries and an accumulated target texture. Geometry changes require `setScene` again; skinned BVHs are still built synchronously in the documented async setup. The public source handles instancing, skinning and material packing, but those paths have not been exercised here. [WebGPU API](https://github.com/gkjohnson/three-gpu-pathtracer/blob/149c7f57b16e6a5a99fc9d182316a446d41ea6a2/src/webgpu/API.md), [scene/update implementation](https://github.com/gkjohnson/three-gpu-pathtracer/blob/149c7f57b16e6a5a99fc9d182316a446d41ea6a2/src/webgpu/WebGPUPathTracer.js).

A camera can provide a custom ray-generation function, which is useful for specialized rendering. However, the public renderer API does **not** expose a ready arbitrary-ray queue to hit-record batch interface. The repository contains `TraceRayKernel` for queued rays and a richer material-aware BVH subclass; these are implementation-level `src/*` modules, not exports from the public `/webgpu` entry. Source access is useful for an informed adapter, but should not be described as a stable public hit-provider API. [Public exports](https://github.com/gkjohnson/three-gpu-pathtracer/blob/149c7f57b16e6a5a99fc9d182316a446d41ea6a2/src/webgpu/index.js), [queued trace kernel](https://github.com/gkjohnson/three-gpu-pathtracer/blob/149c7f57b16e6a5a99fc9d182316a446d41ea6a2/src/webgpu/compute/wavefront/TraceRayKernel.js), [material-aware BVH subclass](https://github.com/gkjohnson/three-gpu-pathtracer/blob/149c7f57b16e6a5a99fc9d182316a446d41ea6a2/src/webgpu/nodes/PathtracerBVHComputeData.js).

The README supports MeshStandardMaterial/MeshPhysicalMaterial and requires MIS for point, spot and directional lights. The source packs intensity, color, world transforms, spot cone/penumbra, decay, range and optional IES information. Emissive materials are supported without emissive-mesh MIS. This maps well to interior content, but does not prove equivalence with native Lambertian shading or our light units. Roughness 1/metalness 0 alone should not be taken as a calibrated pure-diffuse reference. [README restrictions](https://github.com/gkjohnson/three-gpu-pathtracer/blob/149c7f57b16e6a5a99fc9d182316a446d41ea6a2/README.md), [light packing](https://github.com/gkjohnson/three-gpu-pathtracer/blob/149c7f57b16e6a5a99fc9d182316a446d41ea6a2/src/uniforms/LightsInfoUniformStruct.js).

The accumulated color target is a FloatType RGBA StorageTexture in the working color space; display tone mapping happens in a separate screen material. This is a plausible linear-reference capture path. Disable denoising/upscaling, freeze sampling and explicitly record `clampDirect`/`clampIndirect`: the documented default indirect clamp is 10 and is a bias, so it must not silently enter a reference comparison. [Output target creation](https://github.com/gkjohnson/three-gpu-pathtracer/blob/149c7f57b16e6a5a99fc9d182316a446d41ea6a2/src/webgpu/compute/targets.js), [display stage](https://github.com/gkjohnson/three-gpu-pathtracer/blob/149c7f57b16e6a5a99fc9d182316a446d41ea6a2/src/webgpu/materials/RenderToScreenMaterial.js).

## Vanilla WGSL boundary

The supported BVH path supplies **Three/TSL function and storage nodes**, not an engine-neutral `GPUDevice + buffers + WGSL module` API. Shader source is available under MIT, but producing a vanilla WebGPU host requires an explicit, versioned packing/binding adapter. No tested standalone reuse is established by this audit.

Do not start from the older exported `wgslFn` BVH helpers just because they look easier to copy. Upstream deprecated them because storage-buffer pointer calls fail across platforms and directs users to `BVHComputeData`. [Deprecation and rationale](https://github.com/gkjohnson/three-mesh-bvh/blob/26fc97c5f007b8bd905ec31df9deac5d9d668782/CHANGELOG.md), [deprecated source](https://github.com/gkjohnson/three-mesh-bvh/blob/26fc97c5f007b8bd905ec31df9deac5d9d668782/src/webgpu/bvh_ray_functions.wgsl.js).

The path-tracer source includes asynchronous compute preparation with a three.js r186 capability check and an r185 fallback. That is a useful startup reference, not a measured startup guarantee. The BVH first-hit factory also creates a randomized shader variable name; inspect generated WGSL/cache behavior during the spike before making warm-start performance claims. [Preparation code](https://github.com/gkjohnson/three-gpu-pathtracer/blob/149c7f57b16e6a5a99fc9d182316a446d41ea6a2/src/webgpu/PathTracerBackend.js).

## Proposed separate provider spike

Execution mapping: items1–3 below belong to G3 only after G1/G2 pass. Shading/field integration in item4 waits for G4; a full path-traced reference waits for G6. These are sequential scopes, not concurrent acceptance requirements.

Create an isolated dependency set pinned to these sources and a chosen three r186 patch. Keep existing comparison fixtures and packages intact. The spike should:

1. Use the library builder and `BVHComputeData.fns.raycastFirstHit` to consume a deterministic buffer of world-space probe origins/directions and write primitive ID, object ID, barycentrics, distance, normal, side and hit/miss. Do not build another BVH implementation.
2. Compare hits against the CPU triangle oracle on the shared GLB and analytic thin-wall/backface/nonuniform-transform cases. Verify front/back policy, max-distance rejection and IDs before shading.
3. Move one mesh and call the documented transform refit; then change geometry/instance count and exercise the full rebuild. Verify fresh hit buffers and disposal, including two independent provider instances.
4. Add opaque diffuse hit shading with the existing calibrated directional/point/spot contract and a separate shadow query. Feed those radiance/distance samples into the existing DDGI field rather than replacing the field at the same time.
5. Record dependency/runtime versions, source pins, actual WebGPU backend, bytes, update/build costs and shader preparation. Treat vanilla resource reuse as a later compatibility experiment behind the same ray/hit data contract.

A second isolated spike may use `WebGPUPathTracer` as a linear image/reference renderer with matched material/light conventions, explicit clamp settings and sample convergence. It should not be substituted for the ray-hit provider until its internal interfaces have been reviewed. Source-backed API plausibility is established; local compilation, pixels, performance and vanilla integration remain untested.
