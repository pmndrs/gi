# Audit: where the WebGPU DDGI project actually stands

30 October 2026. This is an independent review of everything up to the `review-baseline-2026-10-30` tag: the web code, the native RTXGI setup, the tests and the process. It was done read-only, plus fresh measurements in Chrome on the RTX 3060 Laptop GPU. It covers the old repository, [DennisSmolek/ddgi](https://github.com/DennisSmolek/ddgi/tree/review-baseline-2026-10-30). File paths below refer to that repository at that tag. The v1 spec that came out of it is [SPEC.md](../SPEC.md).

## The short version

- **What exists:** a fast GPU *probe baker* for small, static scenes made of untextured boxes. It reuses DDGI's storage format and the math is checked carefully. It is not the runtime DDGI system the brief asked for.
- **What was dropped:** moving lights, moving objects, continuous updates, real scenes, textures, sky light and frame-time targets. None of these was rejected openly. Each one fell out of the plan when the agent switched to strict serial "gates" on 29 October, and came back only as "practical gaps" in the handoff.
- **Where the effort went:** mostly into proving things, not building things. There are about 7–8 bytes of test harness, validators and evidence for every byte of renderer, and the last day and a half went to explaining percentage differences against NVIDIA's renderer on one 90-triangle scene.
- **What's worth keeping:** some code and several findings. The verdict is to start a clean package and port the good parts, not to continue on top of this structure.

## What I measured myself

Chrome 156, three.js 0.185.1, RTX 3060 Laptop, 1280×720. These are fresh runs on the current code, not numbers copied from its reports.

| Demo | Bake | Frame time with GI | Frame time without GI |
| --- | --- | --- | --- |
| Two-room (5,120 probes, 90 triangles) | 1.50 s | 18.2 ms median, 30.4 ms p95 | 6.1 ms |
| Interior gallery (240 probes, box room) | 75 ms | 6.1 ms | n/a |
| Two-room on the Intel iGPU (built-in browser) | 27.3 s | not measurable (pane throttled) | n/a |

What these numbers mean:

- **Displaying the GI costs about 12 ms per frame**, in a scene with 90 triangles and with no probe updates running. A production DDGI typically spends well under 1 ms here. The original prototype's target was 0.5 ms at 1440p. The cause is in the code: for every pixel, the shader traces up to 8 BVH rays to check whether each probe can see the surface ([VisibleProbeVolumeNode.ts:148-153](https://github.com/DennisSmolek/ddgi/blob/review-baseline-2026-10-30/experiments/gpu-ddgi/src/VisibleProbeVolumeNode.ts#L148), [:277](https://github.com/DennisSmolek/ddgi/blob/review-baseline-2026-10-30/experiments/gpu-ddgi/src/VisibleProbeVolumeNode.ts#L277)). This was added to make sealed rooms exactly black. It replaces DDGI's cheap distance-based visibility test, which is the main reason to use DDGI at all, and it will get far slower on a real scene with hundreds of thousands of triangles.
- **The update engine is fast enough to run continuously.** Their own G4 numbers come to about 1.2 ms of GPU time per 64 probes × 512 rays. At 256 rays and a 2 ms budget, that is roughly 200 probes per frame, so a kitchen-sized volume could refresh completely several times a second. Running continuously is a scheduling job, not a new engine.
- **The GI toggle isolates this cost.** Turning GI off only skips the ray branch; the texture reads still run. The rays use three-mesh-bvh's closest-hit traversal, which can't stop at the first blocker.
- **Bake time is set by the frame rate, not the GPU.** It processes one 64-probe batch per rendered frame. The 5,120-probe bake is 240 frames of about 6.25 ms. At 60 Hz with vsync that becomes about 4 s, with GI blacked out throughout.
- **Memory is large for the content.** The two-room scene owns 196 MiB of buffers:
  - about 119 MiB for three full float32 copies of the probe field (history, scratch, published), sized for all 6,144 allocated probes including inactive ones;
  - about 48 MiB of shadow-ray scratch sized for the 8-light maximum, whatever the actual light count;
  - a duplicate BVH;
  - an unused 5 MB atlas.

  A sensible layout would use under 40 MiB.
- **There are no native performance numbers anywhere,** even though the native harness has a built-in per-pass GPU timer and a CSV benchmark (F4).
- **There is no steady-state frame-time number anywhere** in the repo's reports. Every performance budget is about how long a full bake takes.

## Why the demos show a dark doorway

This is by design. The demos were built as leak tests, not as showcases.

- **Two-room demo:**
  - It uses the native renderer's camera, with the orbit target set 1 unit in front of the camera in a scene about 340 units wide. Orbiting just spins in place.
  - One of its two views is "Closed room", which is meant to be black.
- **Interior gallery:**
  - It defaults to the `door-spot` fixture, with the camera aimed straight at the doorway ([gallery.js:6](https://github.com/DennisSmolek/ddgi/blob/review-baseline-2026-10-30/experiments/gpu-ddgi/demos/gallery.js)).
  - The spotlight is aimed away from the door.
  - Exposure starts at −3 stops.
  - Two of its three camera presets are black rooms on purpose.
- **Shared by both:**
  - GI disappears completely while baking, because the field only becomes visible when the bake finishes.
  - You cannot move a light or an object, compare against a reference, or see the probes.
  - The automated "demo checks" mostly test that certain views are black.

## Code quality

### The core GPU DDGI code (`experiments/gpu-ddgi/src`)

- **It is a baker, not DDGI.**
  - Every pass uses the same 512 fixed directions, with no random rotation.
  - There is no blending over time (hysteresis). Each pass overwrites the previous one, and indirect light is capped at 3 bounces.
  - Probe classification runs on the CPU, brute force over probes × triangles.
  - There is no probe relocation.
  - Rays that hit nothing return black, so there is no sky.
- **It is hard to read.** All the real logic is about 30 KB of minified-style JS and WGSL: statements chained on 300–900 character lines, single-letter variable names, and uncommented WGSL. Settings are stored as magic indices into a 128-byte parameter block (`f[16]`, `u[14]`). This breaks the HomeFig rule that comments explain the *why* in plain words.
- **It looks configurable but isn't.**
  - `prepare()` accepts `sampleCount` and `probesPerFrame`, then throws unless they are exactly 512 and 64 ([three-host.js:58](https://github.com/DennisSmolek/ddgi/blob/review-baseline-2026-10-30/experiments/gpu-ddgi/src/three-host.js)).
  - It throws on any texture, normal map, vertex color, metalness, alpha or transparency, so a normal glTF interior fails at load.
  - It imports code from another app's folder through a Vite alias (`@legacy/...`).
  - It reaches into renderer internals (`renderer.backend.get(...)`).
- **Edits black out the GI.** `refit()` calls `cancel()`, which sets `publishedVersion=-1`, and the display node then forces GI to zero until a full rebake finishes ([three-host.js:59-61](https://github.com/DennisSmolek/ddgi/blob/review-baseline-2026-10-30/experiments/gpu-ddgi/src/three-host.js)). Changing a light does nothing until someone calls `refit()` and `start()`. The gallery's "Direct lighting" toggle only switches the visible light, so the GI keeps showing bounce from a light that is off.
- **Good parts:**
  - Careful generation/epoch guards so a stale bake never publishes.
  - The octahedral convolution math, checked against a CPU reference.
  - The idea of a plain-WebGPU consumer.
  - Integration through three.js's light-node system, so it works with standard node materials.

### The ray provider (`experiments/gpu-ray-provider`)

- **What it is:** a thin, well-tested wrapper around three-mesh-bvh's unreleased WebGPU ray casting. It was the best-tested code in the repo: an independent CPU triangle oracle, thin-wall and mirrored-transform cases, and a check of one dispatch per batch.
- **Pinning and fragility:**
  - It is pinned to a three-mesh-bvh GitHub commit, and it overrides a private method with hard-coded struct offsets, so library updates will break it silently.
  - The BVH is built on the CPU main thread. Its JS de-indexing is fine at 90 triangles and will stall on a real kitchen.
- **What it supports:**
  - Rigid object motion via refit: yes.
  - Adding or removing an object, or changing a material: a full rebuild **plus a shader recompile**.
  - Alpha cutouts and transparency: construction throws.
  - UVs: none, so textures are impossible downstream.

### The original HomeFig bench (`browser/homefig-bench`)

- The cleanest and most readable code in the repo: commented TypeScript with real explanations.
- It bakes probes by rasterizing cubemaps, which does not scale to real scenes.
- The agent's changes to it are small and mostly sound (e.g. `abs(variance)` → `max(variance, 0)`, alpha as a validity flag, a float16 overflow guard).
- `ProbeVolume`, `ProbeVolumeNode`, `octahedral.ts` and `probeAtlasTSL.ts` are the best base for the display side.

### Path-traced reference (`experiments/pathtracer-reference`)

- **The idea is right:** a calibrated three-gpu-pathtracer as ground truth. It caught a real camera-precision bug.
- **The implementation is single-use:**
  - It is hard-wired to one 96×54 camera in the two-room scene.
  - It uses a different three.js version (0.186.1) from the code it checks (0.185.1).
  - It depends on private internals of the path tracer.
- Rebuild it as a generic tool: "any glTF + camera → EXR".

### Test and evidence machinery (`scripts/`, `artifacts/`, the parity/reconstruction folders)

- **Size:** 93 script files (522 KB), 73 tracked `report.json` files, about 5.7 MB of tracked JSON evidence and about 64,000 words of markdown.
- **Validators check reports against reports.** For example, `images.length===112` and `checks.length===29`, which fail by construction if anything is re-run differently.
- **Gates chain into each other,** producing paths like `f7-final-v2/g5/g4/g3/g1/report.json`.
- **None of it is portable.** The Codex agent's private Playwright install is hard-coded into 26 scripts, `chrome.exe` into 23, and several checks require an adapter named "RTX 3060 Laptop" or NVIDIA Ampere. The root `package.json` declares no dependencies.
- **Most checks need data that isn't in git.** The raw evidence they validate is only on the original machine.
- **About 75% of the Node test suite tests the gate analyzers,** not the GI.
- **The tests require byte-identical repeats,** which rules out the random ray rotation and temporal blending that real DDGI depends on.
- **What matters is missing.** Nothing tests temporal response, moving lights or objects, real assets, textures, frame time, or GI continuity during edits.

## The native RTXGI setup

- **The base choice is right:** NVIDIA's official RTXGI-DDGI 1.3.7 Test Harness, built for Vulkan on the RTX 3060. The fork's changes are reasonably clean: capture and dump tools switched on by environment variables, with defaults unchanged.
- **How it was used is very narrow:**
  - Only NVIDIA's tiny `two-rooms` sample scene was ever loaded. It is not a custom scene.
  - Every native run was a correctness capture. No per-pass timings were recorded.
  - The D3D12 build was never made.
  - Sponza was never downloaded.
  - The native path tracer was never run to convergence.
- **One non-portable change:** device selection was hard-coded to skip any GPU whose name doesn't contain "RTX 3060".
- **Human use:**
  - `Play Vulkan Two Rooms.cmd` works. You can fly around (WASD + mouse) and edit lights in the ImGui panel.
  - The launcher only knows the two-room scene.
  - It starts with debug spheres, ambient occlusion and dither on, so the image doesn't match the web view.
  - There is no shared camera or scene file with the web side.
  - The README omits the useful keys: F2 dumps DDGI textures, F4 runs a 1,024-frame benchmark to CSV, J shows the performance overlay, R reloads shaders.
- **Tools already on this machine:**
  - PIX can capture Chrome's D3D12 backend, so the web and native frames can be timed in one tool.
  - Blender Cycles can produce converged ground truth for the same glTF scenes.

## Process

- **The scope narrowed.** The earliest brief is `browser/homefig-bench/app/CLAUDE.md` plus the archived broad plan. It asked for:
  - re-bakes amortized over frames, "never a blocking spike";
  - hysteresis as "the bridge to continuous and dynamic updates";
  - probe sampling under 0.5 ms at 1440p;
  - a real kitchen GLB;
  - an iGPU path that loads pre-baked data;
  - moved fixtures, furniture and doors, and light changes;
  - a window or exterior;
  - a split-screen A/B view.

  On 29 October the broad plan was archived and replaced by gates G0–G7. None of those gates covers scheduling, temporal response, frame cost, real scenes or editing.
- **The measures of success were the wrong ones.** They were:
  - sealed-room darkness to 1e-10;
  - byte-identical repeats;
  - edit equals a clean rebake;
  - bake time against a deliberately slow baseline (the G4 budget was beaten tenfold, so a later 89% GPU-time regression still "passed");
  - percentage attribution against native.

  These are internal-consistency checks on toy scenes. None of them says whether moving a lamp in a kitchen looks right and runs well.
- **Human review was removed** ("Human approval is not a routine phase gate", PLAN.md). The docs are written for an auditor: acronyms, stacked caveats and number dumps. This breaks the brief's own "no paper-speak" rule.

## Findings worth carrying forward

1. **View bias 6 → 0** cut image error against the path tracer from 18.2% to 12.4% RMS. It was never applied.
2. **Fixed ray directions cause visible structure,** so per-update random rotation matters.
3. **When given the same inputs, browser and native probe fields agree** within 0.1% mean / 0.9% RMS. The port's math is right.
4. **NVIDIA's recursion cap (0.9 vs 1.0)** changes indirect light by about 23%. This must be matched when comparing against native.
5. **Build reference cameras from an explicit basis, not inverse-MVP.** The inverse-MVP approach loses precision at near 0.01 / far 2000.
6. **Batched GPU tracing is about 10× faster than cubemap baking** (G4). It's the right transport.
7. **A three.js pitfall:** a uniform-group bug left materials compiled before GI was published showing stale values (`experiments/gpu-ddgi/SKILL_FEEDBACK.md`).
8. **Research memos worth keeping:**
   - `research/webgpu-threejs.md`: the r186 `LightProbeGrid` incremental baking and the light-node integration seam.
   - `research/ddgi-landscape.md`: the reading list and the interior failure-mode tests.
   - `research/probe-density.md`: the cost formula.
   - `research/homefig-audit.md`: it points to the HomeFig production branch, which already has light-group relighting and invalidation.

## Verdict by component

| Component | Verdict |
| --- | --- |
| GPU update pipeline (`gpu-ddgi/src/core.js`, `shaders.js`) | Port the math, rewrite readably as real DDGI with hysteresis, rotation and a budget |
| Per-pixel BVH visibility | Remove from the default path; keep only as an optional debug/quality mode if measured affordable |
| Display side (HomeFig `ProbeVolumeNode`, octahedral, atlas helpers + agent's fixes) | Keep as the base |
| Ray provider | Keep the interface and tests; add UVs, alpha, instance-level updates without recompiles |
| Path-traced reference | Keep the idea; rebuild as a generic glTF+camera tool |
| `profile-probe.js` (WebGPU call/timestamp counter) | Keep |
| Gate runners, validators, EVIDENCE/GATE JSON, nested reports | Archive; do not maintain |
| Native fork | Keep; make device selection portable, add a scene launcher, start recording per-pass timings |
| Demos | Replace with a viewer built for a human to judge |
