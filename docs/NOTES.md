# Notes: facts worth not relearning

One bullet per fact, each with its source. Add a bullet when something cost you time. Fix or delete bullets that turn out wrong. Group by topic.

## three.js (r187)

- **Shared device:** `new WebGPURenderer({ device })` is supported. When three creates the device itself, it uses a compatibility adapter with default limits: a 128 MB storage-buffer binding and 8 storage buffers per stage. Source: `WebGPUBackend.js:72, 213-254`.
- **Device errors:** three assigns `device.onuncapturederror`. Use `addEventListener('uncapturederror')` and never assign it. Source: `WebGPUBackend.js:281`.
- **three caches node shaders by material properties plus light ids** (`RenderObject.getMaterialCacheKey`, `LightsNode.customCacheKey`), not by `material.version`. `needsUpdate` with an unchanged key reuses the old shader, so to change a light node's code, replace the light (new id). Source: `NodeManager.getForRender`, T1.7.
- **Two `wgslFn`s that include the same WGSL through separate `wgsl()` nodes emit it twice,** and WGSL refuses the redeclaration. Share one function node per module. TSL `.toVar(name)` names share the WGSL namespace with included code (a var named `giCoverage` clashed with the module's function). Source: T1.7.
- **Cube uploads with `flipY`:** three puts cube image i into layer `[0,1,3,2,4,5][i]`, flipped vertically (`WebGPUTextureUtils._flipMap`). Source: T1.7.
- **The Meshlet and Visibility-Buffer pipelines draw only FrontSide, opaque, channel-0 materials;** DoubleSide objects fall back to the standard path. Source: T1.7.
- **Standard materials scale indirect diffuse by (1 − F_ss − F_ms):** a white rough dielectric under a uniform environment reads exactly L. Compare against a plain diffuse host with Lambert. Source: T1.7.
- **pmndrs/sky has no `isSky` flag.** Its exposure is `sky.baker.sky.luminanceScale.value` and its sun `.sunDirection.value`; its `turbidity` is a Mie scale, not Preetham's. Source: T1.7.
- **rollup-plugin-dts ran out of memory** once ddgi-three imported three (it builds a new TS program per file reached through node_modules). Workspace `paths` in `packages/ddgi/tsconfig.build.json` fix it: 4.4 s. Source: T1.7.
- **Wrapping our textures:** `ExternalTexture` wraps a same-device `GPUTexture`. three binds it without allocating or destroying it.
  - Set `image = { width, height, depth }`, or size reads as 1×1.
  - Set `type` to match the sample type: the default is filterable float; use `FloatType` for rgba32float and `UnsignedIntType` for uint.
  - For array views, set `isArrayTexture = true`.
  - For 3D, set `is3DTexture = true` and sample it with `texture3D()`. Without the flag the shader fails with "expected texture_3d<f32>, got texture_2d<f32>". Source: T0.8, `WGSLNodeBuilder.js:1399, 2293-2296`.
  - On reallocation, create a new `ExternalTexture` and assign it to `node.value`; `needsUpdate` throws.
  - Don't touch `textureData.externalTexture`, which is the XR path.

  Source: `ExternalTexture.js`, `WebGPUTextureUtils.js:320-326, 486`, `WebGPUBindingUtils.js:332-383`.
- **External buffers:** there is no supported way to bind them. Fragment-readable GI data must be textures. Compute-only buffers are fine. Source: `WebGPUAttributeUtils.js:104-113, 446`.
- **Registering lights:** r187 replaced `addLight` with `Light.registerNode(NodeClass)`, and `LightsNode` creates one node per light. Copy the `LightProbeGrid` pattern: extend `Light`, register an `AnalyticLightNode` with `updateType = RENDER` and `renderGroup` uniforms. Source: `Light.js:18-22`, `LightsNode.js:233-288`, `LightProbeGrid.js:921`.
- **Light-probe priority slot:** `builder.context.lightProbeIrradiance` plus `lightProbePriority` gives one winner per fragment instead of adding up. `LightsNode.setupLights` adds the slot to `context.irradiance` once. It's undocumented, so pin three and test it. Source: `LightProbeGridNode.js:121-180`, `LightsNode.js:343-347`.
- **What `irradiance` means:** it is irradiance E; the Lambert 1/π is applied downstream. Return E, not radiance. Source: `PhysicalLightingModel.js:786-812`.
- **Toggling lights:** `LightsNode.customCacheKey` includes `light.id`, so adding or removing a light recompiles materials. Toggle with `intensity`. Source: `LightsNode.js:153`.
- **Drawing pipelines:** the Meshlet and Visibility-Buffer pipelines (r187 #35191) clone materials and overwrite `material.contextNode`. Don't inject GI through `contextNode`; a scene `Light` works in every pipeline. Source: `MeshletDrawingPipeline.js:114-117, 222-225`, `VisibilityBufferDrawingPipeline.js:692-712`.
- **Env diffuse counted twice:** `scene.environment` adds diffuse via `iblIrradiance`, separately from probe GI, so diffuse is double-counted. r187 has no switch. Open PR #35017 adds `envMapDiffuseEnabled`. `AmbientLight`, `HemisphereLight` and `LightProbe` also add straight to `irradiance`. Source: `PhysicalLightingModel.js:877-895`, `LightProbeNode.js:68`.
- **PMREM:** since r187 it is a `CubeRenderTarget` (RGBA16F, minimum size 256), sampled by roughness-to-mip. Env "irradiance" is the roughness-1 GGX lobe × π, not a cosine convolution, so expect a small mismatch with DDGI at fades. Source: PR #34585, `EnvironmentNode.js:101, 249-262`.
- **`LightProbeGrid`:** L2 SH, raster cubemap bake, no visibility, re-bakes overwrite values. Sponza (490 probes, 32² faces) bakes in 3.1 s on a Pascal GPU. PR #35174, which adds DDGI visibility, is a stalled draft: Sponza shading goes 3.08 → 4.00 ms (8 probes) or 3.38 ms (4 probes).
- **VXGI:** voxel cone tracing at 128³ by default, gathered as a full-screen pass that needs TRAA. Lights are dynamic; geometry needs full re-voxelization. Introduced in PR #34402 (r186).

- **`wgslFn` resources (T0.8):** a `wgslFn` accepts texture and sampler parameters.
  - Pass `texture()` or `texture3D()` nodes of `ExternalTexture`s.
  - A `sampler` parameter is fed from a filterable texture node and uses that texture's filter and wrap settings. Unfilterable (`rgba32float`) textures have no sampler; use `textureLoad`.
  - Source: `nodes/accessors/TextureNode.js:673-680`, `WGSLNodeFunction.js:58-67`.
- **Device features:** three reads `core-features-and-limits` from the device. When we create the device, request it (and all adapter features we need). Source: `WebGPUBackend.js:258`, T0.8.
- **Env diffuse workaround (r187):** `LightingModel.start` builds all lights, then calls `this.indirect`. Overriding `indirect` on our light node's lighting model lets us scale `iblIrradiance` by 1 − coverage.
  - Only Standard and Physical materials read `iblIrradiance`; Lambert and Phong don't.
  - It costs the multi-scatter and sheen env terms inside the volume. It's fixed at build time.
  - Source: `nodes/core/LightingModel.js:24`, `EnvironmentNode.js:109`, T0.8.
- **Light ordering** in `LightsNode` is by `.id`, which mixes node and object ids, so ties between equal-priority probe lights are unreliable. Give our light a distinct priority. Source: `LightsNode.js:36`.
- **Meshlet pipeline** draws `source.clone()` materials and skips cube render targets. So material-instance patches don't survive it; use the light node. Source: `examples/jsm/pipelines/MeshletDrawingPipeline.js:225`.

- **three's frame counter only advances inside `renderer.setAnimationLoop`.** With a bare `requestAnimationFrame` plus `render()`, frame-based nodes (passes, VXGI's cycle, TRAA jitter) stall or skip frames. Source: T0.5, `Animation.js:87`.
- **GPU timing in three:** `resolveTimestampsAsync` returns only the latest frame's passes. To get all of them, sum `backend.timestampQueryPool.<type>.timestamps`. Intel UHD sometimes returns an end before its start (one case read -3,546 s), so drop those. Source: T0.5.
- **LightProbeGrid:** objects drawn before the first bake read an empty atlas. Draw into a fresh RenderTarget after the first bake step. Source: T0.5.
- **VXGI** fails its depth copy on a renderer created with `antialias: true`; create it with `false`. Source: T0.5.
- **Background compiles:** pipelines compile in the background, and objects are skipped until theirs is ready. Warm up until the draw-call count stops growing before timing anything. Source: T0.5.
- **MRT outputs (r187):** every output except `output` defaults to `NoBlending`, and three clears every MRT target to the scene background unless `mrt.setClearColor(name, color, alpha)` says otherwise. `mrt.setBlendMode(name, new BlendMode(MaterialBlending))` gives an output the material's blending. An output is drawn only once its texture exists (`pass.getTexture(name)`). Source: `MRTNode.js:78, 121, 216`, `WebGPUPipelineUtils.js:131-168`, `WebGPUBackend.js:967`, T1.14.
- **Alternating passes frame by frame can make three CPU-bound** (r187, Sponza, 650 draws): two passes with the same attachments but different light sets (one without the GI light), or a shadow map redrawn under each pass's own context, make three rebuild every render object each frame, at 130–280 ms of CPU per frame, so the GPU idles at about 20% use and its clock drops. Give each variant its own camera and use layers instead of toggling a light, and keep the attachments distinct; a static scene's shadow map can be drawn once (`shadow.autoUpdate = false`). Then it records in about 3 ms. Source: T1.14, `three-composite-sponza`.
- **Reading three's GPU timestamps without stalling** (r187 `WebGPUTimestampQueryPool`): `resolveTimestampsAsync` submits its resolve at once and resets the pool, then maps one shared result buffer. A second resolve while one is pending gets the pending promise. So: draw batch k, await the read of batch k − 1, start batch k's read, and draw on. Keep each pass's label until its own uid is resolved. Uids carry the frame number (`…:f<frame>`), so they don't collide. The pool holds 2,048 queries (1,024 passes) and resolves by itself on overflow. Source: `WebGPUTimestampQueryPool.js:60-230`, T1.14.
- **Half-resolution GI in a composite doesn't pay:** evaluating `giIrradiance` once per 2×2 block and upsampling (bilinear × depth × normal weights) saved only 0.23 ms of the composite's 1.3 ms on Sponza at 1440p (most of the pass is reading its targets), and missed the per-fragment image by 1% mean / 4% p95 (untextured) and 4% / 20% with normal maps: a block shares one normal, while normal maps vary per pixel. The upscaler's lower render resolution does the same job better, with temporal reconstruction. Deleted. Source: T1.14 cost study (PROGRESS 2026-11-06).
- **A composite under `@pmndrs/upscaler` 0.5:** use its composable `upscale(color, depth, velocity, camera, { quality })`, not `upscaleScene` (which builds its own pass). The scene pass needs `velocity` in its MRT and `setResolutionScale(1 / ratio)` (`getQualityModeRatio`). `upscale()` materialises its colour with `convertToTexture` at the drawing-buffer size, so wrap the composite in `rtt(node, null, null, { resolutionScale: 1 / ratio })` first. three's GTAONode sizes itself from the drawing buffer, not from the pass; the composite's own GTAO (`PassSizedGTAONode` in composite.ts) sizes from the pass, so its `resolutionScale` stays relative to the pass. The upscaler's jitter comes from RenderPipeline hooks: render through a `RenderPipeline`; with `outputColorTransform = false` and a float render target set, it reads back linear HDR. Its compute isn't in three's timestamps; `gpuTiming: true` and `node.upscaler.gpuTimings` give it (1.5–1.7 ms at 2560×1440 on the RTX 3060 laptop). It's a dependency of `apps/viewer` only; pages import it from `apps/viewer/node_modules/@pmndrs/upscaler/dist/index.js`. Source: T1.14 cost study, `three-composite-shared/variants.ts`.
- **Two MRT passes over the same scene whose targets differ only in format** (rgba16f against rgba8unorm) reuse each other's render pipelines in r187, and WebGPU rejects the draw ("Attachment state ... is not compatible"). Keep one format per scene, or separate scenes. Source: T1.14 (`three-composite-sponza`).
- **three's GTAO (`ao()`) needs its 16 samples to darken GI enough:** on Sponza's curtained GI (1 m radius) it brings +23% to +4.3% at 16 samples, but only to +15.8% at 8 and +20.4% at 4. Half resolution at 16 samples gives +8.0%. Source: T1.14, `three-composite-ao/run.ts --samples --resolution-scale`.
- **GI composite targets:** 8-bit unorm `giAlbedo` and normal (three's SSGI example's bandwidth saving) miss the composite's match bar on Sponza (mean 0.62%, p95 1.9%, against 0.04% and 0.15% with half floats). Source: T1.14.
- **`builder.material` is the material you assigned** (a classic `MeshStandardMaterial`, say), not the node material three builds from it. Node materials copy the classic `is*Material` flags (`NodeMaterial.setDefaultValues`), so test those flags. Source: `NodeBuilder.js:198, 3628`, T1.14.
- **`pass.contextNode`:** PassNode caches the merged context by the pass's own version, so set `pass.needsUpdate = true` after changing it. `context(existingContext, extra)` keeps every key of both (`getFlowContextData` merges the chain). Shaders are cached by the renderer's context node id and version, so a marked pass gets its own shaders. Source: `PassNode.js:966-985`, `RenderObject.js:1024`, T1.14.
- **Renamed in r185:** `directionToColor` / `colorToDirection` are now `packNormalToRGB` / `unpackRGBToNormal` (the old names warn). `@types/three` 0.187 marks `TempNode` deprecated (extend `Node`, as SSGINode does) and lists an old `PhysicalLightingModel.computeMultiscattering` signature (r187's is `(singleScatter, multiScatter, specularF90, f0, iridescenceF0)`). Source: `Packing.js:43`, T1.14.
- **A light node's `RENDER` update runs inside the render pass's encoder lifetime:** `backend.beginRender` creates the encoder, `_renderObjectDirect` calls `nodes.updateForRender` (the update) for the first object, and `finishRender` submits. So work the update submits to the queue itself lands before that render's own submit (checked on the GPU in `three-composite`; shadow maps render nested before it). It runs once per `render()` that draws a lit object, not once per frame. Source: `Renderer.js:2220-2238, 4078-4089`, `WebGPUBackend.js:1082, 1584`, `NodeFrame.js:280`, T1.14.
- **A still camera's matrices aren't bit-identical frame to frame** in the viewer (rebuilt from position and quaternion each frame: -2.7800000000000002 against -2.78), so `Matrix4.equals` never says "same camera". Compare entries with a small relative tolerance (1e-9). Source: T1.12 phase 2b (`apps/viewer/src/ddgi/frame-change.ts`).
- **`renderer.copyTextureToTexture` from a multisampled render target copies its resolved texture,** and the destination can be a render target that was never drawn to (three creates its texture on the copy). The handy way to keep last frame's picture. Source: T1.12 phase 2b, `WebGPUBackend.copyTextureToTexture`, `Textures.updateTexture`.
- **Debug colours that must mean exactly what they say go after tone mapping:** the viewer's `RenderPipeline` has `outputColorTransform = false` and applies `renderOutput()` to each technique's picture itself, then the technique's `overlay()` draws in display space (0 to 1, what reaches the canvas). Mixing a colour in before tone mapping can't be made exact: three's ACES multiplies by exposure / 0.6 and curves, and sRGB makes a 13% linear weight look like 40%. Checked: the share of full-colour pixels on screen matches the share of pixels whose change reaches the scale under ACES, AgX and Linear. Source: T1.12 phase 2b review fixes (`apps/viewer/src/core/viewer-core.ts`, `ddgi/frame-change.ts`).
- **Opaque node materials always write alpha 1** (`NodeMaterial`: `builder.isOpaque()` assigns 1 when `transparent` is false and `blending` is NormalBlending). To write a marker in alpha, use `blending = NoBlending`. The viewer's renderer clears alpha to 0 (`alpha: true`, three's default), so set `setClearAlpha(1)` around a pass whose alpha you read. Source: T1.12 phase 2b review fixes (`probe-spheres.ts`).
- **Tiny probe spheres look speckled through `@pmndrs/upscaler`** (Quality preset), with alpha 1 or 0 alike: its reconstruction, not the spheres. Source: T1.12 phase 2b review fixes.
- **Hundreds of point lights stall three's default lighting:** it writes shader code for each light into every material, and with 1,024 point lights the page's main thread was blocked for more than 30 s (the runner's DevTools call timed out; the GPU sat idle). `ClusteredLighting` (`three/addons/lighting/ClusteredLighting.js`) loops over a per-cluster list instead, but only for lights without `castShadow`, and a light with `distance = 0` goes into every cluster (capped by `maxLightsPerCluster`, extras dropped). Its light texture is `maxLights` wide, so it can't hold more than the 8,192 texture limit. Source: T2.1, apps/viewer/src/render/scene-lighting.ts.
- **Clustered lighting with unranged lights costs every pixel every light:** `sponza-candles`' 1,024 candles (`distance` 0) drew at 0.4 s a frame on the RTX 3060 at 1280 x 720 once the shaders were built, and DDGI's start-up frames, sharing the GPU queue, never finished in 240 s. With a reach (`distance` > 0) and three's default cluster size (32 px, 24 slices): 9 frames a second at 6 m, 18 at 4 m, 33 at 3 m (headless, not under the clock rule). The three adapter reads `distance` as GI's range too. Source: T2.8, `render/scene-lighting.ts` (`limitClusteredLightReach`).
- **A WebGPU canvas can be copied with a 2D `drawImage` straight after `ViewerCore.renderThroughLoop()` resolves** (the same task as the frame, before the browser presents it): the viewer-recording page's JPEGs show the frame just drawn (Chrome 156, RTX 3060). Source: T2.8, `tools/gpu/pages/viewer-recording`.
- **A light the host moves reaches GI a frame late unless its world matrix is updated:** `ThreeGI.update` runs before three's render and reads world matrices as the last render left them (three-gi.ts). The response meter saw it as a step whose own frame didn't move (frame 1 equal to before, then 11.8% at frame 2). The viewer calls `updateLightMatrices` after every light it moves (`lighting/motion-player.ts`). Source: T2.8.
- **`TransformControls`' gizmo is not GI-safe in the scene:** its picking plane is a 100 km `PlaneGeometry` hidden by `material.visible = false` (the object stays `visible`), and it flips its handles' `visible` every frame. The three adapter follows `object.visible`, so in the GI scene it would copy the plane and churn handles. Keep gizmos and markers in a scene of their own, drawn after the main one (`LoadedScene.helpers`). Set `getRaycaster().layers` when they live on a layer of their own, or it can't pick them. Source: T2.8, `TransformControls.js:1910`.
- **three r187 renders a shadowed light's shadow map at intensity 0:** neither `LightsNode`, `AnalyticLightNode` nor `ShadowNode` tests the intensity. Hide the light, or leave it out, to save the passes. Source: T2.1.
- **Release the device between pages:** destroy the device on `pagehide`. Otherwise the next page in the same browser waits on the old page's GPU memory; Bistro exterior then interior took 121 s, against 26 s once the device was destroyed. Source: T0.5.

## Babylon.js (9.33.2, checked 2026-11-04)

- **No device input:** `WebGPUEngine.initAsync` always calls `requestAdapter` and `requestDevice(deviceDescriptor)`. Pass our limits and features in `deviceDescriptor`, and hand `engine._device` to the core. `dispose()` calls `device.destroy()`, and after device loss Babylon requests a new device itself. Source: `webgpuEngine.pure.js:443, 481, 503-520, 3176`.
- **Wrapping our textures:**
  - `wrapWebGPUTexture` leaves the view null and sets no flags. Set `is2DArray`, `is3D` and `type` yourself (FLOAT for `rgba32float`, so the layout is unfilterable), then call `updateWrappedWebGPUTexture`.
  - Disposing the wrapper destroys our `GPUTexture` unless `_hardwareTexture.reset()` runs first.
  - Source: `webgpuEngine.pure.js:1981, 2014, 2999`, `webgpuHardwareTexture.js:88`.
- **Material plugins:**
  - Declarations go in `CUSTOM_FRAGMENT_DEFINITIONS`, the call in `CUSTOM_FRAGMENT_BEFORE_FINALCOLORCOMPOSITION`. Zero `finalIrradiance` to turn env diffuse off.
  - Samplers are found by a `Sampler` name suffix, and `<texture>Sampler` binds to that texture.
  - `vec4f` uniforms need `hardBindForSubMesh`.
  - Babylon is left-handed, and its env irradiance is E/π.
  - Source: `pbr.fragment.js:107, 621`, `webgpuShaderProcessorsWGSL.pure.js:35, 510`, `pbrBaseMaterial.pure.js:1561-1577`, `sphericalPolynomial.pure.js:187-199`.

## three-mesh-bvh (checked 2026-11-04)

- **Version and shape:** v0.9.18 (3 Nov 2026, MIT); default branch `master`. The WebGPU path is `three-mesh-bvh/webgpu` (`BVHComputeData`). It runs only inside three's node system (TSL `FunctionNode`s, three r185+), not on a bare `GPUDevice`, and its API is marked unstable. Source: `src/webgpu/BVHComputeData.js:83,144-149`.
- **Layout:** 64-byte nodes with both child boxes (Aila–Laine, PR #945); triangles as a u32 index buffer plus interleaved `vec4f` positions; 4 storage buffers; a 60-entry stack. Two levels: SAH clusters (at most 64 primitives) under a top level, with per-instance entries; `updateTransforms()` refits the top level only, and skinned meshes are baked on the CPU. Source: `packBVHBufferUtils.js:9`, `ClusteredBVH.js:138-209`.
- **Benchmark trap:** the per-mesh trees from `new MeshBVH(geometry)` default to the CENTER split, not SAH (`Constants.js:80-84`). Pass `{ strategy: SAH }` for a fair comparison.
- **Speed claims:** the "about 2×" upstream gains were *build* times (PRs #942/#943). The Aila–Laine layout gave about 1.12× on raycasts (PR #945, no hardware stated). No published rays/s figure exists. This corrects SPEC's "roughly doubled ray throughput" line.
- **three's `RayTracedRadiosity`** flattens static meshes into one world-space geometry and doesn't use the top level. It was merged to three master on 2 Nov 2026 (#35302), after r187.

## WebGPU

- **Compatibility mode:** devices may allow 0 fragment-stage storage buffers. Keep fragment-side data in textures.
- **Compatibility mode refuses `rg32uint` (and the other `rg32*` formats) as storage textures;** `rgba32uint` and `r32uint` work. A platform texture that hit shading binds is in every DDGI kernel, so one such format breaks DDGI on compatibility devices (`ddgi-shading-compat`). Source: T2.3 (the light grid's picks).
- **Readback:** texture-to-buffer row pitch must be padded to 256 bytes. Source: the HomeFig DDGI branch.
- **Scissor:** it doesn't limit a WebGPU clear. Source: the HomeFig DDGI branch.
- **`pack2x16float` truncates on the RTX 3060** (Chrome 156, D3D12): values packed to halves read on average 0.035% low (the mean of a truncation over half-float mantissas), and up to one half-float step (0.098%) off, not half a step. WGSL leaves this rounding to the implementation, while `pack2x16unorm` and `pack2x16snorm` round to nearest by definition. So every half-float store is a small fixed bias, not noise: DDGI's ray results carry it (−0.035%), and a value stored twice carries it twice. Use stochastic rounding (DDGI's `ddgiStochasticHalf`, `gi/direct`'s `giDirectStochasticHalf`) where a value is stored again or must average out. The Intel UHD shows the same offset between the deferred and inline fields (+0.036%), so it truncates too. Source: T2.2, `hit-shading-deferred` (every case read −0.035% before `gi/direct` rounded stochastically, within ±0.005% after).
- **`textureStore` to an `rgba16float` storage texture truncates on the RTX 3060 too:** the sky bake's radiance map read 0.035% low against the CPU sky (every channel, every sky) until a procedural sky's calibration was measured on the stored map. Source: T2.6a, `hit-shading-sky`.
- **What makes a compute kernel slow to compile here** (Chrome 156 on D3D12, RTX 3060, each pipeline alone in a fresh profile): code written out, not the arithmetic. M1's sky projection, with 18 inlined copies of a workgroup reduction (barriers and a loop each), took 640 ms; the same work with one reduction in a loop over the values, 60 ms. Even 19 `subgroupAdd(vec3f)` calls written out, with no barriers, took 400 ms, against 80 ms in a loop. But a loop that indexes a private array puts it in local memory, which is slow to run: keep loops for subgroup operations and barriers, and write out plain arithmetic with constant indices. Source: T2.6a.
- **Compile times measured inside a start-up include waiting for Chrome's compile workers:** about 25 pipelines compile at once, and each one's time from `createComputePipelineAsync` to its promise is 1.5–2× its time alone, and moves by ±30% between runs. The sky bake's kernels start first since T2.6a. Source: T2.6a, `ddgi-batch-cost` startup.
- **Chrome sends WebGPU calls to its GPU process only when the JavaScript task ends,** so a `createComputePipelineAsync` followed by long synchronous work in the same task starts compiling only after that work. Measured (Chrome 157, RTX 3060): 4 kernels that compile in 91 ms alone, then a 1 s busy loop: 1,080 ms in the same task, 1,001 ms with a `setTimeout(0)` between them. To compile while copying a scene in, call `prepare()`, let the task end, then copy (`GIVolume.start` does since T2.14). Source: T2.14 (a temporary page, not kept).
- **One compute pass can hold a dispatch that writes indirect arguments and the indirect dispatch that reads them,** because each dispatch is its own usage scope. But a buffer can't be both writable storage and the indirect buffer of the *same* dispatch, so `gi/direct`'s arguments live in their own buffer, not in the ray scratch it binds. Source: T2.2.
- **Hidden tabs** do no GPU work, so benchmarks must run in a visible or headless-active page. Source: the HomeFig branch, and this project's audit (the built-in browser pane throttles when hidden).

## Tooling and environment

- **Choosing the GPU in headless Chrome:**
  - Chrome 156 gives NVIDIA by default, whatever `powerPreference` says.
  - `--use-webgpu-power-preference=force-low-power` makes `requestAdapter()` return null.
  - The Intel GPU is reached with `--use-adapter-luid=<high>,<low>`. LUIDs change every boot; the runner reads them with `Get-PnpDeviceProperty` on `{60B193CB-5276-4D0F-96FC-F173ABAD3EC6} 2`.
  - `--disable-gpu` makes `requestAdapter()` return null.
  - Intel reports architecture `gen-12lp`.
  - Source: T0.2, `tools/gpu/chrome.ts`.
- **WGSL errors arrive late:** shader-module errors surface only after the queue drains. `runGpuTest` waits about 50 ms after the drain; anything later can be missed. Source: T0.2.
- **Node runs `.ts` directly** (Node 24 type stripping), but rejects enums, namespaces and constructor parameter properties. The root tsconfig has `allowImportingTsExtensions` for `.ts` import paths. Source: T0.2.

## Ground-truth renderers (T0.7)

- **Cycles units** (`tools/reference/cycles/units.py`):
  - Sun strength = lux.
  - Point power P = 4πI watts, from candela.
  - Emission strength = radiance.
  - A spot keeps the point's I on its axis.
- **Cycles axes:** three (x,y,z) maps to Blender (x,−z,y). three's Euler XYZ order is the reverse of Blender's.
- **Cycles has no light range window.** three r187 point lights fade to 0 at `distance`, so three is about 12% dimmer than Cycles at 7 m on two-room.
- **Blender defaults that bias references:** indirect clamp 10, light threshold 1%. Turn both off.
- **Always run Blender with `--factory-startup`.** A user add-on on this machine makes Blender hang at exit.
- **three-gpu-pathtracer (WebGPU):**
  - `maxBounces` counts the camera hit as 1.
  - Emissive meshes are found only by scattered rays, so Cornell's ceiling lamp is noisy. Point lights are sampled explicitly.
  - Its default `clampIndirect` is 10; set it to 0.
  - The accumulation texture is rgba32float, readable from `backend.get(target).texture`.
- **FLIP:** `python -m flip_evaluator.flip_python_api`, which needs no numpy.
  - Run it with `python -E`, not `-I`, because `-I` hides the user site-packages where it is installed.
  - FLIP numbers are comparable only at the same downsample.
- **Comparing noisy renders:** average over 8×8 blocks before judging. Two Cycles seeds differ by 0.8% per pixel but by 0.1% per block.
- **Blender's glTF importer links Metallic and Roughness to the metallicRoughness texture.** A linked socket ignores its value, so unlink it before setting it. Principled's Diffuse Roughness (4.3+) above 0 means Oren-Nayar. Source: T0.7 follow-up.
- **The references are pure Lambert; three's standard material isn't.** `scenes/src/three-scene.ts` uses `MeshStandardMaterial` (roughness 1, metalness 0, F0 0.04). That adds a rough specular lobe the Cycles and path-tracer references lack, worth a few percent of the full image. When comparing the viewer against a reference, render with `specularIntensity = 0`, or measure the gap first, so the GI error isn't mixed with material error. Source: T0.7 Opus review.
- **`@pmndrs/denoiser` is not on npm.** Build steps are in `tools/reference/README.md`.

## Sky (T1.1)

- **Radiance `.hdr` readers disagree:** three's HDRLoader reads the mantissa as m/255, stb_image as m/256, Blender as (m+0.5)/256, up to 0.4% apart. Use half-float EXR for shared HDR data. Source: `HDRLoader.js:358`.
- **three's PMREM against a cosine integral:** under the open-ground sky, PMREM environment diffuse on flat ground reads R/G/B −0.04/−0.61/−0.97% (diffuse-only material).
- **Blender's equirect matches three's `equirectUV`** after the (x, −z, y) axis mapping, with no rotation. `--calibrate` checks it to 0.00%.
- **three's EXRLoader** stores rows bottom-up with `flipY` false, so `equirectUV` reads it the right way up. Source: `EXRLoader.js:2469`.
- **Native harness sky:** one constant `skyRadiance` in ProbeTraceRGS, PathTraceRGS and GBufferRGS by default; nothing tells rays above the horizon from rays below. Since T2.7 the fork can read the sky file instead (`scene.skyTexture`, `play.ps1 -Sky texture`, Vulkan only): `GetSkyRadiance(direction)` in `Descriptors.hlsl`, with the image's `Tex2D[]` index and a blend share packed into `LightingConsts`' old padding word (0 = the flat sky).

- **L2 SH misses ±0.5% sky irradiance under our Preetham skies** (up to 0.9%); adding band 4 brings it under 0.35%. Band 3's cosine weight is 0. Source: T1.4.
- **three r187 WebGPU equirect textures put the nadir at memory row 0** (`isFlipY` is false in WGSL), and environment rotation samples at Rᵀd. three samples a non-render-target `CubeTexture` with x negated, so its cube maps come out mirrored against a plain convention. Source: T1.4 and its review.
- **Shadow-ray offsets:** Wächter–Binder's per-component ulp offset tilts along the surface when the coordinates differ in size, and leaked 8 thin-box corner hits. T1.4 pushes along the normal, scaled by the largest coordinate, and nudges the point into its triangle. Before the nudge, 25 of 1,200 barycentric corner hits landed just outside the neighbouring face. The offset grows with distance from the origin, so far-off thin walls can still leak (comment at `platform/shade/wgsl.ts`). Source: T1.4.
- **Nearest-sampled (rgba32float) rotated skies shift by up to half a texel.** Source: T1.4.
- **The platform bakes a procedural sky on the GPU since T2.6a** (Preetham per direction from per-sky numbers the CPU works out, `procedural-sky.ts`; calibrated on the stored map). A bake costs 0.039 ms of GPU (median, RTX 3060 loaded, VALID) and 0.004 ms of CPU, and runs when the sun has turned more than 0.05° since the last bake, or turbidity, intensity or sunIlluminance changed. The bake is its own timed pass, `platform/sky bake`, not counted in a technique's budget. Source: T2.6a, `sky-rebake-cost`.
- **Bands 0, 1, 2 and 4 miss more than ±0.5% of the ground's sky irradiance at a very low or very high sun:** against the CPU sky's own integral, a 5° sun (turbidity 2) reads +2.3 / +1.0 / −0.4%, an 89° sun (turbidity 1.7) +3.5 / +1.7 / +0.7% (R / G / B); 12° to 60° suns are within ±0.5%. Only the open-ground and Sponza skies are held to ±0.5%. Source: T2.6a, `hit-shading-sky`.

## Platform scene copy (T1.2)

- **Scene copy memory:** octahedral normals (4 bytes) and 16-bit indices for meshes with at most 65,536 vertices. Intel Sponza's base package (2.05 M vertices, 3.75 M triangles) takes 87.7 MB. `sponza` with the curtains (5.74 M triangles) takes 130.1 MB, 97% of the 128 MiB default storage binding, and `sponza-full` 348.5 MB, so large scenes need raised limits (`node tools/bench/scene-copy-memory.ts`). Bistro exterior takes 111.4 MB, which fits the 128 MB default binding only because of the octahedral normals. uv1 costs 16 MB on Sponza, so adapters should pass `uvs1` only when a material samples channel 1.
- **Scenes that need raised limits** (default `maxStorageBufferBindingSize` 128 MiB = 134.2 MB). The tracer's triangle records take 48 bytes per triangle; the scene copy figures come from `node tools/bench/scene-copy-memory.ts`:
  - `sponza` (base + curtains, 5.74 M triangles): scene copy 130.1 MB (fits, just); tracer records about 276 MB (needs raised limits).
  - Sponza base only (3.75 M): scene copy 87.7 MB; tracer records 179.9 MB (needs raised limits).
  - `bistro-exterior` (2.83 M): scene copy 111.4 MB; tracer records about 136 MB (needs raised limits).
  - `sponza-full` (12.8 M): scene copy 348.5 MB; tracer records about 616 MB (needs raised limits).
  - `bistro-interior` (1.04 M) and every procedural scene fit the defaults.
  - Both laptop GPUs allow about 2 GiB (DECISIONS 2026-11-05).
- **`Omit<Union, K>` keeps only the keys shared by every member,** so `Partial<Omit<LightDescriptor,'type'>>` couldn't name `position` or `range`. Fixed with `LightChanges`.
- **Bind-group layouts in budget tests must be explicit.** An `'auto'` layout drops bindings the entry point doesn't use, so it can hide an over-budget kernel.
- **WebGPU ordering:** a `queue.writeBuffer` made during `encode` lands before the host's submit of that encoder, and copies recorded in the encoder run after it. So a growth copy must never cover a range written in the same frame.
- **What a moved instance costs on the CPU in Chrome on this laptop** (T2.M1, `scene-set-transforms`): 10,000 `setTransform` calls 15-20 ms; one `setTransforms` started at 9 ms and came down to 1.4 ms sliding (3.5 ms turning). What helped: the box and the move distance from one world frame (a corner and three edges, not eight corners, ~2×); merging regions as they come once a frame passes 256; copying a few numbers by hand instead of `TypedArray.set`; not inverting again when only the translation changed; and the per-slot state in flat typed arrays (`InstanceTransforms`). For slides, one pass rewrites only the translation and the box. Also: no keyed lookups by string in the loop, a branch-free finite check with four sums, and reusing the lookups for the same list. What didn't: unrolling the record stores. **Chrome runs this code about 1.5-2.4× slower than Node 24, and code fed two typed-array kinds (Float32 and Float64) slows down for both.** Keep the hot path on one kind, and time workloads in blocks, not frame by frame in turn. Run to run the same code read ±0.3 ms while other agents used the CPU, so time it under both locks (`--cpu-timed`). Source: T2.M1.
- **Only `giInstanceBounds` reads an instance record's world box;** the tracer's top levels make their own boxes (CPU `transformBounds`, GPU instance-box pass), and the scene tests compare at 1e-5. So the record's box need not be bit-identical to `transformBounds` (T2.M1 builds it from a frame). Source: T2.M1.
- **TypeScript narrows a getter chain after a check:** after `assert(platform.stats.recompiles === 0)`, a later `platform.stats.recompiles` has type `0`, and comparing it with 1 fails to compile. Read such counters through a function. Source: T2.M1, `platform-recompiles`.
- **Meshes are packed on the GPU since T2.13** (`gi/pack-mesh`, `gpu-mesh-packing.ts`): `createMesh` stages the host's raw arrays with `writeBuffer`, and the next `encode` packs them. Only after `prepare` has called `PlatformScene.prepareGpuPacking`; a scene that never prepares (tools, unit tests, the `scene-copy` page) and a mesh too large for one staging buffer still use the CPU packer. The GPU's octahedral normals differ from the CPU's by at most one step: about 0.2% of Sponza's 3.1 M normals are one step off on both GPUs (5,632 on the RTX, 5,608 on the Intel UHD). `gi/pack-mesh` took 5.1 ms of GPU on Sponza (RTX, GPU shared with another process) and 72 ms on the Intel UHD, once per load. Source: T2.13, `scene-gpu-packing`.
- **What the scene copy's main thread spends on Sponza after T2.13** (Chrome 157, this laptop, other work on the CPU; T2.13 profile): the raw upload (`writeBuffer` of 144 MB) 115-160 ms, the checks (`planMesh`: highest index, box) 100-120 ms, the tree builders' copies of positions and indices 45-70 ms, the rest of the three scene sync about 95 ms, and texture averages 0.29 s. The raw upload alone is near 150 ms, so the main thread can't get much below that while it copies 144 MB. Source: T2.13.
- **Texture averages read through a GPU-backed canvas wait for the GPU** (three adapter, `texture-average.ts`): `getImageData` on an `OffscreenCanvas` drawn on the GPU waits for the GPU to finish. Sponza's 55 images took 0.46-0.67 s, Bistro exterior's 145 took 4.25 s (most of T1.9's 4.1 s scene copy), and Sponza's took 26 s while another process kept the GPU at 100%. A CPU canvas (`willReadFrequently: true`) took 0.16 s and 1.1 s, and its averages are as close to a full-resolution linear average as the GPU canvas's (mean error 2.7% against 2.8% on Sponza, 2.4% on both for Bistro; both downscale to 256 px in sRGB). The two canvases' linear albedo averages barely differ: mean 0.07% on Sponza's 29 albedo maps (max 2.2%, one map) and 0.04% on Bistro's 132 (max 4.2%). `ddgi-sponza-accuracy`'s indirect mean is the same to 9 digits. Source: T2.13.
- **In Chrome 157 no route reads an `ImageBitmap`'s pixels off the main thread**, so texture averages can't simply be made asynchronous. Measured on Sponza's and Bistro exterior's three-loaded images (55 and 135), main-thread time:
  - `createImageBitmap(bitmap, { resizeWidth, resizeHeight, resizeQuality: 'high' })` resizes inside the call: 122-132 ms and 0.80-0.84 s.
  - Cloning the bitmaps to a worker (`postMessage`, no transfer) blocks for 170-218 ms and 1.8-1.9 s, and the main thread stayed blocked until the worker answered: 0.4-0.54 s and 3.5-3.8 s in all.
  - `queue.copyExternalImageToTexture`: 120 ms and 1.16 s in the calls, plus 0.26 s and 0.83 s blocked after.
  
  Transferring would detach three's own images. The CPU canvas (0.16 s and 1.1 s) stays the cheapest. Off the main thread, averages would have to be made where the image is decoded (the loader's worker, from the file's bytes). Source: T2.13.
- **The tree builders' copies of positions and indices can't be dropped without a contract change:** the host keeps its arrays (three keeps them for raycasting and bounds), so they can't be transferred, and `postMessage` cloning copies on the main thread too. The scene makes one copy at `createMesh` and transfers it to the worker. Source: T2.13.

## Texture store (T4.1)

- **The store is an `rgba8unorm-srgb` texture array written by `copyBufferToTexture`, not by storage writes.** `gi/texture-store` makes each level in a float scratch buffer (linear light, for the next level's average) and as sRGB-encoded rgba8 rows in a byte buffer, which is copied into the layer. Why: an sRGB format can't be a storage texture, and the alternative (an `rgba8unorm` array with an sRGB view, plus storage and sampled views of single levels and layers bound side by side) is refused on compatibility-mode devices, which bind a texture only whole and with the view dimension it was made with. The array starts at 2 layers, because a 1-layer texture defaults to a `2d` binding in compatibility mode. `ddgi-shading-compat` passes on the Intel UHD with the store bound in every DDGI kernel. Source: T4.1.
- **Every source kind makes the same layer** (`textures-sources`, both GPUs): `PixelData`, `ImageData`, an `ImageBitmap` made with `premultiplyAlpha: 'none', colorSpaceConversion: 'none'` through `copyExternalImageToTexture` (alpha 128-254 kept exactly), an `rgba8unorm` `GPUTexture` and BC7 all match to the byte; an `rgba8unorm-srgb` `GPUTexture` (decoded by the hardware instead of the kernel) is within 1/255. Level 0 of a 256² image is the image exactly (the sRGB round trip through f32 linear is lossless). Source: T4.1.
- **A BC7 test image without an encoder:** mode 6 blocks with both endpoints the colour and every index 0 decode to exactly that colour, for any colour whose channels are all even (the p-bit is shared). `tools/gpu/pages/textures-shared/textures.ts`, `bc7SolidBlock`. Source: T4.1.
- **What the store costs:** 0.35 MB a layer (256² × 4 bytes × 4/3). 506 layers took 177 MB. Making 500 textures (32² to 512²) in one frame took 0.34 s to submit and finish on the RTX 3060 and 1.05 s on the Intel UHD, staging uploads included. Source: T4.1.
- **Texture sampling at hits matches a CPU sampler to the filter hardware's precision:** on the uv board, the worst channel is 0.0073 off on the RTX (an emission of 1.9) and 0.0029 on the Intel UHD, mean 0.0003 and 0.00015, over 6,912 hits with mip 0 and ray-cone mips, head-on and at 50°. Source: T4.1, `textures-uv-board`.

## Tracing (measured)

- **Materials in the walk are behind triangle flag bit 0** ("consult the material"; T4.2). Builders leave it clear; `gi/triangle-flags` (trace/triangle-flags.ts) sets it from the scene copy on every placed tree (`rays.requestTriangleFlags(meshSlot)` is the install hook: any new path that writes tree triangles must call it) and when materials change. The `rays` module now depends on the scene module, so a batch kernel binds 7 of 8 storage buffers. The low-level `TraceBatchKernel` (oracle, trace bench) has no scene copy: its `giMaterialPasses` returns false, so it measures the walk without materials. Source: T4.2.
- **A flagged ray costs about nothing on a small scene:** any-hit on the glass-pane case, pane see-through (flagged) against opaque (no flags), 1,012 against 1,011 Mrays/s on the RTX 3060 and 117 against 118 on the Intel UHD (1M rays, GPU timestamps). Not measured on foliage or with alpha tests yet. Source: T4.2, `trace-materials`.
- **A DDGI page run twice on one GPU gives the same numbers to the last digit** (the glass-pane page, the field means), so a before/after comparison of code that shouldn't change the field can use one run of each: two-room and Sponza's atlas means before and after T4.2 differed by under 1e-8 (relative). Source: T4.2, `ddgi-field-unchanged`.

- **Any-hit should visit the farther child first.** A shadow ray starts on a surface, so the nearer child is mostly that surface, and the blockers lie ahead. On the RTX 3060 that was 1.2–2.8× faster than nearer-first; closest-hit is unaffected. Source: T1.3.
- **Leaf size is not why three-mesh-bvh won at any-hit.** It is faster at leaf 4 than at its default 10. Source: T1.3.
- **Reading triangle corners through the scene copy's index buffer costs 10–30% of trace speed,** so self-contained 48-byte records stay. Source: T1.3.
- **Both laptop GPUs allow storage bindings of about 2 GiB** in Chrome 156 (`maxStorageBufferBindingSize` 2,147,483,644; `maxBufferSize` 2,147,483,648). Source: T1.3.
- **tinybvh builds over NaN positions without complaint,** so `buildMeshBvhWithTinyBvh` refuses non-finite positions. Source: T1.3.
- **`active` is a reserved word in WGSL,** and using it as a name fails shader creation. `refit-cpu.test.ts` scans the refit shader for such names. Source: B1a.
- **One adapter makes one device.** A page that needs a second device (for example one without subgroups) must request a new adapter. Source: B1a.
- **Subgroup sizes on this laptop:** RTX 3060 32 (min 32, max 32); Intel UHD 8 to 16. Source: B1a.
- **The GPU top-level refit** takes 0.084 ms for 10k moving instances on the RTX 3060 and 0.44 ms on the Intel UHD. Box reads through atomics never needed their bounded re-wait to give up on either GPU. Source: B1a.
- **An instance's world box** is the box around the mesh box's eight transformed corners, which is looser than the box around the transformed vertices when the mesh is rotated. Tests must compare against the corners. Source: B1a.
- **Morton codes need cubic cells, not one stretched to 1024 cells per axis.** Stretching each axis (HIPRT's plain `computeMortonCode`) made LBVH trees of flat or long meshes cost 2.4-2.6 times tinybvh's SAH (a flat grid, a slab, a rod); cubic cells over the mesh's longest side gave 1.02-1.22, and cubes are unchanged. Real meshes are often walls, floors and curtains. Source: B1, CPU twin (`lbvh-cpu.ts`).
- **Building many meshes one by one on the GPU is dispatch-bound.** A per-mesh LBVH (about 40 dispatches each) took 97 ms of GPU time for Sponza's 132 meshes, while its largest mesh alone took 2.3 ms. One batch for all meshes (mesh and tile tables, a segmented sort) took 32-42 ms. Source: B1, `bvh-lbvh-profile`.
- **An atomic load that every thread does on the same word serialises.** On D3D12 an atomic load is a read-modify-write: six of them per thread on one mesh's bounds cost 23 ms in the Morton kernel for 5.7M triangles. Read such words through a plain read-only binding of the same buffer in a later dispatch. Source: B1.
- **The LBVH climb is not bound by how many words it hands over.** Halving them (leaves aren't handed over) left it at about 13 ms on Sponza, and a two-round climb (first round up to 64-triangle nodes) only took it to 11.7 ms. It is still the build's slowest step. Source: B1.
- **An indirect dispatch costs about 0.022 ms on the RTX 3060 in Chrome 156 even when it runs no workgroup** (`dispatchWorkgroupsIndirect`; Dawn checks the arguments with a dispatch of its own), against about 0.002 ms for a direct one-thread dispatch. Three in a pass made T2.4c's propagation cost 0.07 ms on every still frame. For work sized on the GPU, prefer a direct dispatch of a few hundred workgroups that loop over the list (0.010 ms for the whole empty pass). Source: T2.4c, `ddgi-key-probes-cost` with each dispatch timed on its own.
- **A loop bounded by a value from a read-only storage binding may hold `workgroupBarrier`:** WGSL's uniformity analysis counts `var<storage, read>` as uniform (unlike `atomicLoad` on a read-write one, NOTES above). `ddgi/propagate` loops over its list's length that way. Source: T2.4c.
- **`from` and `target` are reserved words in WGSL** (Chrome 156 refuses them as parameter names). Source: T2.4c.
- **A WGSL float literal must be representable after rounding:** `3.4028235e38` (the largest f32 as JavaScript prints it) is refused ("cannot be represented as 'f32'"); `3.0e38` is fine. Source: T2.3.
- **A kernel that reads the same small table once per workgroup is bound by those reads, not its arithmetic:** the light grid's build read every packed light (48 bytes) for each of 4,096 cells, twice (about 400 MB a frame) and took 0.28 ms on the RTX 3060 whatever the threads per cell or the arithmetic; taking out parts showed it. Loading 128 lights at a time into workgroup memory for 16 cells cut it to 0.19 ms. Find the cost by taking parts out before rewriting arithmetic. Source: T2.3, `ddgi-light-grid-cost`.
- **`pass` is a reserved word in WGSL too, and a `let` in a function body can't reuse a parameter's name** (a `@builtin(num_workgroups) groups` parameter and `let groups = ...` fail as a redeclaration). Source: T2.5.
- **The kernel builder moves WGSL directives to the top** (`hoistDirectives` in kernel-builder.ts): platform modules come before a technique's code, and `enable subgroups;` after a module's declarations fails ("directives must come before all global declarations"). So a technique may write its `enable` at the start of its own code even when it lists modules. Source: T2.4a (`ddgi/mark` with the light-falloff module).
- **The platform's light falloff is a binding-free module, `HitShading.lightFalloff`** (`giShadeDistanceAttenuation`, `giShadeSpotAttenuation`; hit shading depends on it). A kernel that needs a light's unshadowed irradiance without tracing can list it alone. Source: T2.4a.
- **Changes made while the budget is paused are kept for the techniques' next frame** (`mergeSceneChanges`, gi-platform.ts). Before T2.4a they were dropped: the platform doesn't call techniques on paused frames, and the three adapter's first sync runs paused, so DDGI never saw the scene's creation. A light changed during a pause would never have been marked. Source: T2.4a.
- **The scene copy keeps its own copies of light vectors** (position, direction, colour): a host that edits an array in place and passes it to `updateLight` again no longer changes the stored "before" state the change log compares. Source: T2.4a.
- **`target` is also a reserved word in WGSL, and a function can't share a name with a module-scope variable.** `wgsl-names.ts` checks every B1 shader for both. Source: B1.
- **LBVH trees trace slower than tinybvh's even at a similar SAH cost.** Sponza (5.7M triangles): SAH 1.22x tinybvh's, closest-hit about 0.8x and any-hit about 0.8x of tinybvh's Mrays/s on the RTX 3060; see `trace.csv` for the recorded medians. Source: B1.
- **CWBVH (compressed 8-wide nodes) was not faster than our BVH2 in WebGPU on the RTX 3060.** Same tinybvh trees, same rays, median of 3: closest-hit about 1.0× on Sponza (0.96× with BVH2 timed first, 1.02× with CWBVH first) and 0.82× on Bistro interior, with nodes 3.9–4.6× smaller (whole scene 28–32% smaller). CWBVH's speed stayed flat from 1264 to 1530 MHz while BVH2's rose, so it isn't held back by the SM clock. The paper's 1.9–2.1× was on CUDA. Source: B3.
- **When one page times two tracers back to back, the second runs about 6% slow** on the power-limited RTX 3060 (B3: CWBVH ÷ BVH2 was 0.957× with BVH2 timed first and 1.016× with CWBVH first). Alternate the order, or time each on its own from a cool start. Source: B3.
- **Quantized child boxes need a margin.** The GPU rebuilds each plane as `origin + q·2^e` and then `(plane − ray origin) · invD`, which cancels for rays starting near the node: 1.7% of edge-aimed rays slipped through on the Intel UHD with tightly quantized boxes (tinybvh rounds each plane outward to the next step, no further). Quantizing every plane at least 1/1024 of a step outside the triangles fixed it on both GPUs. Source: B3.
- **Keep a two-level walk in one loop.** CWBVH with the top level in one loop and a mesh walk called inside it (tinybvh's shape) ran 0.69× of BVH2 on Sponza; one loop over both levels ran 0.96×. Source: B3.
- **Two triangles sharing an edge give watertight distances about 2e-7 apart (relative),** so two tracers on different trees can pick different triangles at an edge. Compare closest hits with a tie tolerance (the oracle uses 1e-5). Source: B3.
- **H-PLOC trees are close to tinybvh's best build; LBVH trees are not.** Sponza (5.7M triangles, CPU twins, `tools/bvh/tree-quality.ts`): H-PLOC with B1's 30-bit cubic codes and SAH leaf collapse 1.034x tinybvh's default build's SAH cost; with tinybvh's 63-bit stretched codes 1.078x; tinybvh's own `BuildHPLOC` (one triangle per leaf) 1.172x; the LBVH 1.217x. The cubic codes beat tinybvh's here, as they did for the LBVH. Source: B2.
- **tinybvh's H-PLOC chains the tree on exact area ties.** Its nearest-neighbour search takes the first of equal candidates (+1 before -1), so with equal merged areas every cluster picks its right neighbour, one pair merges per round, and the tree becomes a chain: 3000 identical triangles give depth 128 (the tracer's stack holds 64). Regular grids tie often. Our H-PLOC pairs ties up instead (`tieBreak: 'pairs'`, the default; depth 9 there), which also made a 1.8% cheaper tree on a test grid; `tieBreak: 'tinybvh'` keeps tinybvh's rule for comparisons. Source: B2.
- **Time GPU builds back to back, not one at a time.** A build that waits for its result before the next lets the GPU drop its clocks in between: the furnished room's H-PLOC build took 24 ms that way and 2.4 ms with 400 builds submitted back to back; Sponza's 47.7 ms against 45.3 ms. The trace bench reports both (`build_gpu_ms_*` single, `build_gpu_loaded_ms_*` back to back for about 10 s); the loaded one is the pass/fail number. Source: B2.
- **The RTX 3060 Laptop is power-limited under the H-PLOC build even from a cool card:** started at 62–63 C, the SM clock stayed at or below 1,380 MHz (median 1,012) with the power limit in 63% of the loaded samples, so these rows get `note/clock_low`. Shorter or lighter GPU work reaches 1,800–2,050 MHz. Source: B2, `trace-bench-hploc-build-sponza`.
- **One atomic counter per mesh, bumped by every merge round, is not where H-PLOC's climb time goes** on Sponza (taking it out bought about 5%), but numbering nodes without it is simpler anyway: a merge names its node after the representative leaf of the cluster it absorbs. Source: B2.
- **First mesh trees from the GPU (T2.12):** the platform builds the scene's meshes, as first loaded, with H-PLOC in one batch (its own submit, then a stats readback of a few words per mesh), copies each usable tree into the tracer's shared buffers, and lets tinybvh's tree replace it when the worker finishes. A mesh's first tree is whichever arrives first; a GPU tree arriving after tinybvh's is dropped. Swapping changes one range and one mesh-table entry: Sponza's 449 meshes swapped in one frame with 0 compiles and the field's mean moving −0.0019% (normal frames 0.0004-0.003%; VALID run, T2.12 PROGRESS). `rays.building` covers first trees only; `rays.refining` and `whenRefined()` cover tinybvh's. Code: `trace/gpu-mesh-trees.ts`, `trace/ray-queries.ts`; DECISIONS 2026-11-08. Source: T2.12.
- **tinybvh's trees have slightly more nodes than H-PLOC's** (Sponza: 3.03 M against 3.01 M; triangles are the same), so swapping them into a node buffer that the GPU trees filled exactly doubled it (193 to 386 MB). Placing GPU trees now asks the node buffer for an eighth of headroom when it grows (`GrowableStorage.grow`'s `headroom`, applied when that is larger than doubling); tinybvh-only growth is exact, as in M1. Source: T2.12.
- **Sponza's start-up with GPU first trees** (RTX 3060, cold, VALID, quiet machine; median run): handoff to first GI drawn 1.90 s = `prepare` 1.12 s (the scene copy's CPU 1.10 s; compiles done 8 ms later) + first GI frame 0.30 s (uploads, the GPU build sent, tinybvh's copies) + first trees 0.01 s (GPU build 82 ms to its stats; all 449 meshes on GPU trees) + placing 0.04 s + first warm-up step 0.10 s + three's first frame with the GI light 0.33 s (its material compile 0.32 s, in series). tinybvh's trees are all in 3.8 s after the handoff. Source: T2.12, `timing.csv`.
- **three's `compileAsync(scene, camera)` culls against the camera and compiles for the canvas's render context** (r187, `StandardDrawingPipeline.isCulled`; pipelines depend on the render target and MRT). So a library can't usefully pre-compile a host's materials for it: hosts draw through their own passes. Source: T2.12 (why check 1 counts three's GI compile in series).
- **A fake device with `subgroups` in a unit test starts the real H-PLOC**, which fails on the fake's empty pipelines (the platform then warns and uses tinybvh). Tests of the top level pass `meshTrees: { gpuFirst: false }`; tests of the swap give a stand-in `firstTreeBuilder` (mesh-tree-swap.test.ts). Source: T2.12.
- **A per-node clear with strided stores costs 3x a flat fill.** H-PLOC's clear of 12 words per node took 2.8 ms of Sponza's build; one vec4 per thread over the whole buffer, 0.9 ms. Source: B2.
- **`@diagnostic(off, subgroup_uniformity)` on a function lets subgroup operations run in control flow that is uniform in the subgroup but not the workgroup** (a loop every lane of a subgroup stays in until `subgroupAny` says stop). Chrome 156 accepts it on the RTX 3060 and the Intel UHD. WGSL's uniformity analysis only knows workgroups, so without it such loops don't compile. Source: B2.
- **A value from `atomicLoad` is non-uniform to WGSL's analysis,** so a loop bound or `break` on it in a kernel with barriers fails to compile ("workgroupBarrier must only be called from uniform control flow"). Have one thread store it in workgroup memory and read it with `workgroupUniformLoad`. Source: T2.4b, `ddgi/schedule-fill`.
- **WebGPU doesn't promise that a 1-D workgroup's subgroups hold consecutive threads in order,** which a scan built from subgroup scans needs. `ddgi/schedule-fill` checks it on entry (`subgroupBroadcastFirst(thread) + subgroup_invocation_id == thread`) and takes its workgroup-memory scan when it fails; on the RTX 3060 and the Intel UHD both scans give the same list. Source: T2.4b.
- **WGSL allows override-sized arrays only in workgroup memory.** A per-thread array sized by a pipeline-overridable constant fails shader creation; generate the size into the WGSL instead. Source: B2.
- **The device reports its subgroup sizes:** `device.adapterInfo.subgroupMinSize` / `subgroupMaxSize` are 32 / 32 on the RTX 3060 and 8 / 16 on the Intel UHD (Chrome 156). The H-PLOC sizes its per-lane cluster slots from the minimum. Source: B2.
- **A NaN corner doesn't make a NaN box on the RTX 3060:** WGSL's `min` and `max` returned the other operand, so a GPU builder builds a finite tree around a NaN triangle instead of failing. Don't rely on the builder to catch NaN input (ddgi-core refuses non-finite positions before tinybvh). Source: B2.
- **Use a watertight triangle test.** Möller–Trumbore let 3–12% of rays aimed at shared edges slip between triangles (RTX 3060 11.6%, Intel UHD 3.0%, 2M rays each), and leaked into sealed thin boxes. The watertight test (Woop et al. 2013, with stored corners) let none of 4M through. Source: `tools/gpu/pages/trace-oracle`, T0.10.
- **Don't index a vector with a per-ray value in WGSL.** `a[kx]` with a runtime `kx` cost about 40% on the RTX 3060 (Sponza 61 → 101 Mrays/s once removed). Build per-ray row vectors with `select()` once per ray instead. Source: T0.10 part C.
- **Read BVH nodes and triangles as `array<vec4f>`:** one 16-byte load each gave +3% on the RTX 3060 and +23% on Intel UHD. Source: T0.10 part C.
- **Traversal stack depth:** Sponza needs 35 entries and Bistro exterior 44. A 32-entry stack was no faster than 64, so 64 stays. Source: T0.10 part C.
- **tinybvh in WASM:** its fast builder needs `__AVX__`. Emscripten emulates 256-bit AVX on WASM SIMD from 3.1.68 on; with `-msimd128 -mavx`, `Build` runs the SIMD Bonsai builder (Ganestam et al. 2015): Sponza in about 1.5 s in Node, with the lowest tree cost of tinybvh's builders. With 3.1.57 only the scalar builder compiled (4.9 s). pthreads would need cross-origin isolation (COOP/COEP headers), which a library can't require of its hosts. Rebuild with `pnpm bvh:wasm` (pinned emsdk in `tools/emsdk/`). Source: T0.10 part C, B0.
- **V8 turns scalar WASM float selects into branches.** Box loops written as `a < b ? a : b` cost 2.5× on Sponza. Use `f32x4.lt`/`gt` with `v128.bitselect`. `f32x4.min` and `fminf` treat −0, +0 and NaN differently from the JS conversion, so they'd break byte identity. Source: B0b.
- **Sponza under tinybvh:** 115 meshes of at most 85k triangles; 1.91 M nodes, about 2 triangles per leaf; WASM memory stays around 67 MB. tinybvh's own Build (about 1.45 s) is now most of the build time. tinybvh builds the same tree twice from the same mesh (tested). Source: B0b.
- **Every browser with WebGPU also has WASM SIMD** (Chrome 91+, Firefox 89+, Safari 16.4+), so no scalar WASM build is needed. Source: B0.
- **JS memory speed on this laptop:** just reading 300 MB takes about 110 ms, so a JS pass over a Sponza-sized tree costs 100-300 ms whatever the code does. Move such passes into WASM or onto the GPU. Source: B0.

## DDGI (measured lessons)

- **After a sun turn, a probe update costs more than its rays say for about 12 frames:** on Sponza at about 780 MHz, frames 0-11 after a 30° turn traced 13,500-17,500 rays (a still frame 17,300-19,900) yet took 2.15-2.49 ms against about 2.0. `gi/direct` lit 6,600-7,700 hits against 4,850 still (0.69-0.71 ms against 0.58), and `ddgi/trace` took 1.27-1.44 ms against 1.18 for fewer rays. Later frames match their rays. Frame-to-frame spread on still frames is itself about ±0.1 ms at this clock, and the same page's medians move 2.00-2.23 ms between runs. Source: T2.18, `ddgi-key-probes-cost` `firstFramesPasses`.
- **Cutting the batch where every key owes its full count breaks the key round:** the furnished room's 448 active keys converge together only while the priority share (428 of 571) lists nearly all of them each frame. At a cut batch the most urgent keys spent their owed updates first, against keys that had not moved yet, and its sun step settled at frames 162 / 124 instead of 11 / 13. Source: T2.18 (DECISIONS 2026-11-08).

- **Half-float atlases with hysteresis 0.97 need stochastic rounding:** round-to-nearest stalls the furnace 4.6% low. Source: T1.5a.
- **Hysteresis trades noise against settling, and theory predicts both.** For a texel with per-update noise σ and hysteresis h, the change per update is about σ·(1−h)·√(2/(1+h)): Cornell's per-pixel change went 0.56% → 0.095% at h = 0.995 (predicted 6.0× quieter, measured 5.9×) and 0.155% at 0.9917 (predicted exactly). Bounce light that hasn't settled shrinks only by about (1−h)(1−ρ) per update, so at 0.995 every-frame updates need about 3× the frames of 0.97 on the furnace (1800 against 600) and 5× on the two-room scene (3000). Source: T1.12 phase 2a.
- **A running average whose estimates read the field it is building settles bounce light slowly:** with h = k/(k+1) the bias shrinks only like k^−(1−ρ), so estimates made early against a dark field linger until the clock fades them. Cornell (ρ ≈ 0.65) came out of a 16-pass warm-up 26% low. Weighting later updates more (h = k/(k+a), the ramp) makes it shrink like k^−a(1−ρ): −10.5% at a = 3, about −6% at a = 8. A small fixed cap on the count does worse. An endless a = 8 keeps every-frame probes noisy for a·nMax updates (0.28% a frame 400 frames after the warm-up), so the ramp lasts only a probe's first 16 updates. Source: T1.12 phase 2a follow-up.
- **DDGI's probe history is readable for debug tools:** `DDGIField.probeHistory` is the storage buffer `ddgi/blend` keeps n, t and k in, `PROBE_HISTORY_WORDS` words per probe in probe-index order (`PROBE_HISTORY_WORD` gives the offsets; a unit test ties them to the WGSL struct). To draw it in three, copy n into a texture with a small compute pass (`apps/viewer/src/ddgi/probe-history.ts`). Source: T1.12 phase 2b.
- **The probe history is 48 bytes a probe since T2.4a** (m2-lights.md §4.1; `PROBE_HISTORY_WORD` in layout.ts), and the buffer has `COPY_SRC`, so tests can copy it out. `k` is the low 16 bits of word 2 now. Words 6-7 hold the probe's mean irradiance (rgb halves) and noise, written by every blend. Source: T2.4a.
- **After a light step, the error that lingers is the old light's bounce, not the new light's arrival.** A probe's new estimates bounce off neighbours that still hold the old light, so probes cut too gently keep it for seconds, and a GI view can overshoot (two-room's 2 m lamp step: +3.9% at most, then +2.0% after 2 s, with every probe updated every frame). The depth of the cut (`lightChangeScale`) decides it, not who is marked. Source: T2.4a, `ddgi-change-step`.
- **A converged two-room field holds its value at h = 0:** 60 frames of the fixed rule at h = 0 (every update replaces the probe) stayed within ±1% of the converged mean (noise, no drift), so a low h causes no bias by itself. (The run meant to test h = 0.3 too ran at h = 0, under the bug below.) Source: T2.4a diagnostic.
- **On the GPU, `x / (x + 1)` with x = 3e38 gives 0, not 1:** the division goes through a reciprocal, 1 / 3e38 is a denormal, and denormals flush to 0. T2.4a's "no cut" stand-in made the fixed hysteresis rule read h = 0 until it was caught (the still page now covers the fixed rule). Guard "no limit" values with a `select`, or use a stand-in whose reciprocal is a normal float (below about 8e37). Source: T2.4a, found by `ddgi-flicker` on Sponza.
- **A still scene with T2.4a's change-driven history gives M1's field to the last digit on the RTX** (`ddgi-change-still`, 600 frames, Cornell and two-room): with no marks the blend's arithmetic is unchanged. Use that page to check that later dynamic-update work leaves still scenes alone. Source: T2.4a.
- **The viewer's scene target is half float, so the change-per-frame view bottoms out at about 0.05-0.1%:** on settled Cornell about 20-25% of pixels change by exactly 0 between frames, and the rest move in single half-float steps or more. Source: T1.12 phase 2b readback.
- **Rules compared inside one ddgi-flicker run need a `units:` budget, not `gpuMs:`:** the platform calibrates at the first `gpuMs` frame, partway through the page's frames, so one rule got 440 Sponza probes a frame and the next 26. Source: T1.12 phase 2a.
- **DDGI reads high where irradiance changes fast near surfaces:** Cornell's true irradiance rises 12–21% over the first 0.5 m off the floor, and probes buried in slabs make it worse. Source: T1.5a's path-traced irradiance check.
- **One kernel that traces, shades and blends is register-bound:** a split trace-and-shade kernel plus a blend kernel ran 2× faster on the RTX 3060 and 1.5× on Intel. Source: T1.5a.
- **Both laptop GPUs offer `texture-formats-tier1`** in Chrome 156, so DDGI's distance atlas is `rg16float`. Source: T1.5a.
- **Decoded ray directions in workgroup memory** (12 KB of 16 KB) made the update 21% faster than recomputing them per texel. Source: T1.5a.
- **A big-change test on a probe's own noisy estimate biases the field:** per texel +8%, on the probe's mean +22% on Cornell. Deciding from the previous update reads 1.8 points low instead. Source: T1.5b.
- **32 fixed rays miss surface slivers near the corners of the reach box;** at a reach of 1.5 spacings no needed probe switched off on Cornell or the cabinet row. Source: T1.5b.
- **Coincident faces of touching solids defeat ray-based inside tests:** probes can sit a few mm inside a board and stay active. Source: T1.5b.
- **After the trace/blend split, the Intel UHD spends about half its DDGI update time in the blend kernel.** Source: T1.5b.

- **After a light change, DDGI's response is set by the bounces, not by the history:** each update's estimate bounces off the field as it is, so even an update that keeps nothing of the old value (h = 0) shrinks the error by only ρ, the share of a probe's light that comes back through the field. Two-room's ρ is about 0.8 (its lamp halved, 82% of the probes updated a frame at h ≈ 0: the error shrank 0.84 a frame), Cornell's about 0.65. So a full change needs about ln(0.05)/ln(ρ) updates, 14 on two-room, whatever the cut. A count that grows back by one an update after a cut averages the stale estimates in, and the error then shrinks only like k^−(1−ρ). Source: T2.4b, `ddgi-schedule-step` (DECISIONS 2026-11-06).
